# array-test × auth-service 驗測流程與驗收契約

狀態：2026-11-04 的流程設計與現況 review，**不是已完成的整合功能或實際服務驗收**。後續已取得 `array-line-demo` @ `7264cca` 與 `auth-service` @ `4b5473b`，核對了標準 OIDC＋PKCE 與本站 session 契約，詳見 [實際串接盤點](ARRAY_LINE_DEMO.md)。實際部署／Google 登入與 Dashboard adapter 仍待驗證，以下原則依已確認的 Worker 契約落實。

## 1. 一次建立測試專案，分清服務角色

主目標為 array-test，但不能把所有請求都送到 array-test。每個測試專案包含以下角色；開發機／QA 等環境是這些角色的一組網址與非機密設定。

| 角色 | 要設定／辨識的內容 | 用途 |
| --- | --- | --- |
| 應用程式 | array-test 網址、登入入口、應用 callback | 觀察登入流程、state、前端 session 與頁面行為。 |
| 身分服務 | auth-service issuer、discovery、實際 token／refresh／logout 契約 | 取得與更新 token、SSO session、輪替與撤銷。 |
| 受保護 API | API origin、唯讀驗測路徑、成功資料的識別方式 | 證明 token 是否真的換到應用能力；可能與 array-test 同源，也可能分開。 |
| 測試身分 | 測試使用者 A／B、角色與允許範圍的代號 | 建立合法與越權對照；不把帳密放進專案設定。 |

如果 array-test 只有靜態前端，HTML 頁面回 200 不代表受保護資料可讀，必須找出它真正呼叫的 API。不能在未讀原始碼前猜測 array-test 是否有 BFF、cookie session、JWT API 或 UserInfo。

環境只保存各角色的目標網址。路由契約依實際串接的 adapter 定義；client ID、redirect URI、scope、憑證與變更條件都在各情境填寫。可以透過明確操作選用一份測試配方，但不得偷偷繼承其他情境的參數、secret、token 或 session。

## 2. 第一個畫面先做「準備檢查」

主流程：選專案／環境 → 準備檢查 → 選攻擊目的 → 填此情境參數 → 執行與比較 → 檢視證據／匯出。

準備檢查由使用者按下才開始，逐項顯示：

- 目標、issuer、API 能否連線；端點回應是否符合契約。
- demo 實際使用哪一種協定：標準授權碼交換、JSON＋refresh cookie，或其他已核對的 adapter。
- 瀏覽器從哪個 origin 發出請求；需要哪些 cookie／CORS 條件。
- 此環境支援哪些情境，哪些沒有實作相應功能。非支援的 grant 不混成已完成的安全測試。
- 測試帳號 A 能否完成真實 demo 正常登入，並讀到指定受保護 API 的預期資料結構。
- 未登入的獨立瀏覽器 context／HTTP client 對同一 API 是否確實受限。

HTTP 200、/health 成功或 discovery 可讀，只證明那一步正常，不能代替「登入並讀取受保護 API」。SSO cookie、瀏覽器 callback 與同站條件要保留原始紀錄，不能一律以貼 token 取代。

如果有效對照沒有建立，依原因顯示「缺設定／連線失敗／登入未完成／API 契約不符／目標限流」，保留修正入口；依賴它的攻擊情境不得顯示成功或被防護阻擋。獨立的公開端點盤點仍可執行，但不能冒充整合驗收。

## 3. 依攻擊目的分組，不讓使用者猜 OAuth 術語

| 使用者目的 | 主要操作目標 | 所需條件與對照 |
| --- | --- | --- |
| 沒登入，能否直接讀資料 | 受保護 API | 有效登入對照＋未登入請求；判讀真正的資料回應。 |
| 拿到 access token，能做到什麼 | array-test 所使用的 API／UserInfo | 此情境的 token、資源路徑、成功識別條件；比較未登入與合法對照。 |
| 別的使用者／client 憑證能否越界 | 受保護 API | A／B 的合法憑證及原本允許範圍；避免用原本就無效的憑證當作跨權限測試。 |
| 登入 callback 能否被冒用或重播 | 應用 callback 或身分服務 callback | 明確區分兩種 callback 與各自的 state；使用真實瀏覽器交易與對照。 |
| 登出、過期或輪替後，舊憑證還能做什麼 | 應用 API＋身分服務 | 有效初始狀態、時間條件及專案預期政策；不把未到期 JWT 仍可用自動當漏洞。 |
| 拿到 client secret、code 或 refresh 憑證 | 身分服務，必要時再到 API | 只顯示實際協定支援的情境；標準 grant 和 JSON＋cookie adapter 分開。 |
| 真實瀏覽器是否允許跨站操作／讀回 | demo、身分服務及測試用外部 origin | 真實瀏覽器 origin、cookie、preflight、回應可讀性；Node 人工加 Origin 不能代替。 |

第一個完整驗收切片應是「正常登入 → 取得 app 實際使用的憑證 → 正常 API 對照 → 未登入／持有 token 比較 → 明確結果 → 匯出」。它跑順後，再加入 callback、跨權限、輪替與瀏覽器跨站類別。

## 4. 一個情境只做三步

### 填參數

右側顯示本情境的目的、會打哪個角色／網址、必要輸入與具體副作用。端點與專家設定預設收合，常用輸入直接顯示。憑證以來源代號（例如 token-A）辨識，不在標題、紀錄或報告顯示原值。

- 每個情境有自己的草稿，不共用 secret／token。
- 可以明確按「使用準備步驟的測試身分 A」建立本情境的執行期副本；不得靜默共用可消耗的 code／refresh token。
- 需要 code、一次性 state 或有效 cookie 的情境，使用真實流程準備；不要求使用者憑空填不存在的值，也不要求前端 JavaScript 讀取 HttpOnly cookie。
- 缺必填值、過期憑證或錯誤路徑，在執行前提示；不得因缺參數而送出一串必然失敗的請求。
- 會消耗 code、輪替 refresh、撤銷 session 或觸發限流的情境，事前明確顯示影響；執行後提示是否需要新交易／重新登入。

### 執行與比較

先確認本情境有效對照，再只變更所測試的條件，執行一次有限操作。執行中顯示目前步驟與正在互動的角色，可停止。並行、重播、時間邊界等情境由 handler 明確控制步驟與次數，不能用全域「執行全部」混用同一組消耗型憑證。

JWT audience、expiry 等控制若要分別判定，必須有符合其測試前提的憑證。單純改 claims 造成簽章同時失效，只能證明該竄改 token 被拒絕，不能宣稱獨立驗證了 audience／expiry。

### 看結果與下一步

先顯示「攻擊者實際做到了什麼／沒做到什麼」，再顯示證據與限制。技術回應隨右側結果欄捲動，不另建立 response 內層捲軸。

| 結果 | 必須具備的證據 | 使用者下一步 |
| --- | --- | --- |
| 操作成功 | 有效前提、實際能力的契約證據、對照差異 | 對照預期權限／安全政策判讀影響。 |
| 本次操作被阻擋 | 有效前提已成立，收到可歸屬於該應用／協定的拒絕 | 檢視阻擋原因與覆蓋範圍。 |
| 未能判定 | 缺參數、對照失敗、協定不適用、WAF／限流或證據不足 | 指出具體原因、需重新準備的資料與重試步驟。 |
| 執行錯誤／已停止 | 網路、TLS、逾時、取消等執行層資訊 | 修復連線或重試；不計作防護成功。 |

HTTP 2xx、顯示登入頁、WAF challenge、SPA shell 都不能單獨證明「讀到受保護資料」。需核對 Content-Type、API schema／識別欄位與契約中的成功條件；個人資料只做最小化比對，不放入匯出報告。403 HTML 也不能直接證明是 app 的權限控制。

不將操作成功自動等同漏洞；登入登出、token TTL、refresh 寬限等政策要以實際專案為準。每個未驗證／不適用項目要列出，不能被摘要中的綠色通過數掩蓋。

## 5. 不同角色的憑證路由

不能因加入多個 origin 就放寬成任意轉送憑證。

- client secret、refresh cookie、授權碼只到明確設定且契約允許的身分服務端點。
- access token 只到明確選擇的 API／UserInfo 角色；不把 issuer 的 cookie 順便轉送給 API。
- discovery／redirect 指向未設定的 origin 時停止，不自動信任或帶憑證追蹤。
- 真實瀏覽器場景使用隔離 context，依交易保留 cookie 狀態；HTTP 情境使用獨立傳輸，不把兩者結論混合。
- 跨角色執行、取消、限流與清理都有明確狀態；已完成的步驟保留證據，不把停止後未執行的步驟算通過。

## 6. 驗收清單

以下都未宣稱已針對 array-test 完成；整合時逐項附執行紀錄。

- [ ] 核對 array-test／auth-service 的版本、登入／callback／token／API 契約。
- [ ] 一組測試環境可正確保存不同角色的目標；切換環境不殘留前一組憑證。
- [ ] 真實 demo 可正常登入，測試 A 可讀預期 API，未登入對照確實無法讀取。
- [ ] API 的 200 登入 HTML、錯誤 JSON、WAF 回應與錯誤路徑均不會顯示能力成功。
- [ ] 不支援的 grant、過期 code、無效 token、缺 cookie 不會顯示防護已通過。
- [ ] 至少一個已知允許與一個已知拒絕的情境，結果符合實際服務；弱化 fixture 只能作測試器回歸，不能替代這一步。
- [ ] 情境 A／B 的參數、結果及草稿互不混用；修改參數後舊結果不計入目前結論。
- [ ] 消耗型交易可重新準備；重跑不會悄悄沿用已消耗 code／已輪替 refresh。
- [ ] 取消、逾時、429、錯誤端點與重新登入後可恢復，沒有卡住的執行狀態。
- [ ] 瀏覽器類情境確實在瀏覽器執行，不用 Node 結果冒充 CSRF／CORS／SameSite 證據。
- [ ] 桌面／筆電可看到目前目標、所選情境與執行狀態，左右獨立捲動，response 無內層捲軸；手機流程也可完成。
- [ ] 匯出含版本、角色／目標、情境與設定版本、時間、對照、實際證據、限制及未完成項目，不含憑證與個人資料。
- [ ] 本機 checkout／啟動方式和交付分支正確；不能要求使用者從尚未更新的 main 驗收新功能。
